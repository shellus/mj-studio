# 对话压缩系统设计

## 概述

对话压缩系统通过 AI 生成摘要来减少上下文大小，同时保持缓存友好以降低 API 成本。

## Anthropic 缓存机制

### 缓存计费原理

Anthropic API 支持 Prompt Caching，当请求的消息数组前缀与之前的请求一致时会命中缓存：

- **缓存写入（Cache Write）**：首次发送时按写入价格计费（略高于普通输入）
- **缓存读取（Cache Read）**：后续请求命中缓存部分按读取价格计费（约为普通输入的 10%）

**关键**：缓存命中依赖**消息数组前缀完全一致**。

### 缓存前缀构成

API 请求结构：
```
systemPrompt (独立参数) + historyMessages (消息数组) + userMessage (当前输入)
```

缓存前缀 = `systemPrompt + historyMessages`

只要这个前缀保持不变，后续请求就能命中缓存。

## 消息标记类型

系统使用 `mark` 字段标记特殊消息：

| 标记 | 说明 | 是否进入 historyMessages |
|------|------|------------------------|
| `SYSTEM_PROMPT` | 对话维度固化的系统提示词 | ❌ 否（提取到参数） |
| `COMPRESS_REQUEST` | 压缩指令消息 | ✅ 是（压缩时）❌ 否（普通消息时） |
| `COMPRESS_RESPONSE` | 压缩摘要消息 | ✅ 是 |
| 无标记 | 普通用户/助手消息 | ✅ 是 |

## SystemPrompt 处理机制

### 双重存在形式

SystemPrompt 在系统中有两种形式：

1. **助手配置**：`assistant.systemPrompt`（助手维度，所有对话共享）
2. **对话消息**：`MESSAGE_MARK.SYSTEM_PROMPT` 消息（对话维度，固化某个版本）

### 提取与过滤逻辑

```typescript
// 1. 提取 systemPrompt 参数
const systemPromptMessage = result.messages.find(m => m.mark === MESSAGE_MARK.SYSTEM_PROMPT)
const systemPrompt = systemPromptMessage?.content || assistant.systemPrompt || null

// 2. 从 historyMessages 中过滤掉 SYSTEM_PROMPT 消息
historyMessages = historyMessages.filter(m => m.mark !== MESSAGE_MARK.SYSTEM_PROMPT)
```

**原因**：
- `systemPrompt` 作为独立参数传递给 API（`body.system = systemPrompt`）
- `SYSTEM_PROMPT` 消息不应出现在 `historyMessages` 中，避免重复
- 这样才能保证缓存前缀一致

## 压缩工作流程

### 压缩范围计算

假设当前有 100 条消息，压缩保留数为 4：

```
消息 1-96：待压缩的历史消息
消息 97-100：保留的最近消息
```

### 压缩请求流程

1. **compress.post.ts**：
   - 计算压缩范围（从上次压缩点到保留消息之前）
   - 创建 `COMPRESS_REQUEST` 消息，存储压缩指令
   - 创建 `COMPRESS_RESPONSE` 消息（空内容，status: created）
   - 调用 `startStreamingTask` 开始流式生成

2. **streamingTask.ts**：
   - 提取 systemPrompt（从 `SYSTEM_PROMPT` 消息或助手配置）
   - 构建 historyMessages（从上次压缩点到当前压缩请求，**包含压缩请求本身**）
   - **过滤掉 `SYSTEM_PROMPT` 消息**
   - 调用 `chatService.chatStream` 生成摘要

3. **chatProvider**：
   - 将 systemPrompt 作为独立参数（`body.system`）
   - 将 historyMessages 转换为 API 消息数组
   - 发送请求，流式返回摘要内容

### 压缩边界

压缩边界是压缩摘要在对话中的位置，决定了后续请求的上下文起点。

**压缩前**：
```
systemPrompt + 消息 1-100 + 用户新输入
(约 20,000 tokens)
```

**压缩后**：
```
systemPrompt + 压缩摘要 + 消息 97-100 + 用户新输入
(约 3,000 tokens)
```

### 多次压缩

第二次压缩时，从上一次的压缩摘要开始：

```
systemPrompt + 摘要 A + 消息 97-148 + 压缩指令 → 生成摘要 B
```

这样可以持续减少上下文大小，同时利用缓存（摘要 A 作为前缀保持不变）。

## 缓存友好的实现要点

### ❌ 错误做法：拼接消息内容

```typescript
// 将消息拼接成字符串
const messagesContent = messagesToCompress
  .map(m => `${m.role === 'user' ? '用户' : 'AI'}: ${m.content}`)
  .join('\n\n')

const finalPrompt = compressPrompt.replace('{messages}', messagesContent)

// 发送单条消息
chatStream(modelName, systemPrompt, [], finalPrompt, ...)
```

**问题**：每次压缩时 `finalPrompt` 内容都不同，无法命中缓存。

### ✅ 正确做法：保持消息数组结构

```typescript
// 保持消息数组结构
const historyMessages = messagesToCompress  // 原始消息对象数组

// 压缩指令作为 COMPRESS_REQUEST 消息
const compressRequest = await conversationService.addMessage(user.id, {
  conversationId,
  role: 'user',
  content: compressPrompt,  // 直接存储压缩指令
  mark: MESSAGE_MARK.COMPRESS_REQUEST,
  sortId: compressRequestSortId,
})

// streamingTask 中构建上下文
historyMessages = result.messages.slice(startIndex, compressRequestIndex + 1)
historyMessages = historyMessages.filter(m => m.mark !== MESSAGE_MARK.SYSTEM_PROMPT)

// 发送消息数组
chatStream(modelName, systemPrompt, historyMessages, '', ...)
```

**优点**：
- 历史消息作为独立对象保持在数组前缀
- 压缩指令作为最后一条消息追加
- 缓存前缀 = `systemPrompt + historyMessages`（不含压缩指令）
- 多次压缩时，前面的消息保持不变，命中缓存

### 常见误区

**误区 1**：将消息拼接后放在指令后面

```typescript
// ❌ 仍然无法命中缓存
const content = `消息1\n消息2\n...\n\n请对以上对话进行总结`
messages = [{ role: 'user', content }]
```

问题：整个 content 是一个字符串，每次压缩时内容都不同，前缀无法匹配。

**误区 2**：压缩请求时忘记过滤 SYSTEM_PROMPT 消息

```typescript
// ❌ 可能导致 SYSTEM_PROMPT 消息进入 historyMessages
historyMessages = result.messages.slice(startIndex, compressRequestIndex + 1)
```

问题：`SYSTEM_PROMPT` 消息会被当作普通消息发送，破坏缓存前缀一致性。

正确做法：
```typescript
// ✅ 必须过滤
historyMessages = historyMessages.filter(m => m.mark !== MESSAGE_MARK.SYSTEM_PROMPT)
```
